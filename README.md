# AI Novel Platform

AI 小说平台 —— 阅读 + 管理 + 学习一体化。

## 功能

- **小说阅读**：TTS 朗读、章节导航、进度条、悬浮工具栏；桌面浏览器另在页面两侧提供「上一章 / 下一章」箭头（触屏仍以滑动与方向键为主）
- **AI 问答**：基于章节内容的智能问答，支持语音输入
- **学习模式**：词汇讲解（多语言）、章节测试（选择题）
- **小说管理**：命令式操作（列举/追加/删除章节），支持一次追加多章大纲与区间补写大纲，移动端优先 UI；章节列表/合计/正文弹层都显示**字数**；章节弹层内可**上一章/下一章翻章**，并能「填构思 → 就地生成大纲草稿 → 改完再保存」
- **发布前预览**：先把整本渲染到带 token 的暂存站翻阅，并出一份【修改报告】（包括改了什么、连带影响哪些页、逐页 diff），确认后才写入正式目录
- **VIP 读者授权**：VIP 按读者账号授权（可设到期、可撤销），不再使用共享密码
- **长任务反馈**：生成类操作有遮罩（转圈 + 已用秒数 + 服务端逐章进度），动手前先探推理链路，同一本书生成互斥
- **删除二次确认**：删整本、删单章、区间删除都要手输 `OK`（不是点“确定”就行），三个入口服务端都校验
- **推理服务连接**：控制台登记多条 aibridge API Key 并一键启用，运行时就能看到“现在连的是哪个模型”、切换不用重启（仅超管）
- **分部（部）**：把若干章归为一个“部”，发布时按部成组、每部可带导言页；划分时每部一行、只填「部名 + 到第几章」，**不需要手写 JSON**

## 登录与管理入口

本地启动后（默认端口 3400，默认挂在 `/novel` 前缀下，URL 与线上环境一致）：

| 入口 | 地址 |
| --- | --- |
| 登录页 | http://localhost:3400/novel/login/ |
| 小说管理页 | http://localhost:3400/novel/admin/ |
| 控制台（用户 / VIP 授权 / 推理服务连接，仅超管） | http://localhost:3400/novel/admin/dashboard.html |
| 阅读首页（当前登录用户的作品站） | http://localhost:3400/novel/ |

- 直接访问 `/novel/admin/` 未登录会自动跳到登录页，登录后回到管理页。
- 首个超管账号由 `config/users.json` 播种（首次启动写入 `data/system/global.db`，之后密码以库内为准，改密走控制台“重置密码”）。
- 若把 `BASE_PATH` 置空（挂在根路径），去掉上述地址里的 `/novel` 前缀即可；书页仍挂在内部 `/novel` 挂载点。

## 发布与预览

1. 在小说管理页选书 → ③ 章节列表 → 「👁 预览」。
2. 弹出的【预览 · 修改报告】页（`/novel/admin/preview.html`）展示：总览、结论句、逐页变化原因，可展开单页句级 diff；点「📖 打开预览站」按真实书页翻阅整本。
3. 确认无误点「✅ 确认发布」写入正式目录；若预览后又改过内容，发布会重渲染并告知哪些页发生漂移；「作废预览」则只删暂存产物，不动线上。
4. 发布仍可直接点「🚀 发布」（预览是独立动作，不是硬闸门）；暂存预览默认保留 24 小时，且仅创作者本人登录态可看。
5. 发布会顺带清掉「本次不再产出」的旧页面（已删章节、旧命名或旧分部导言的遗留），避免旧 URL 继续返回过时内容。报告里这类页标为「待下线（发布时删除）」，发布结果会回报实际删除了多少页。
6. 例外：同一账号下若有多本书书名相同（发布目录就是书名，因此共用目录），报告与发布都会跳过上述清理并在结论里提示。此时目录里混着另一本同名书的合法章节页，照常清理等于发布一本删掉另一本；请先把书名改得不一样再发布。
7. **「线上现在是哪一版」只能看磁盘，不能查 `publish_state`**：那张表记的是“上次推到远程的文件清单与内容哈希”，只有 SSH 发布路径会通过 `savePublishManifest` 全量重写它；本地发布（`publishNovelLocal`，这台机器上的默认路径）**根本不写这张表**，于是它长期停在最后一次远程发布的章数——实测线上 20 章而表里只有 10 行，一度被误报成“发布漏了一半”。核对线上请读 `public/novel/<userId>/<书名>/index.html` 与 `chapter_*.html`，或直接跑 `node tmp/verify-publish.mjs`（逐项核：页数量=章数、无孤儿页、目录条目数、每页 H1 章号与位置一致、章名一致、内嵌章节测试与生词表、页面正文逐字收录库内正文、正文引用的章号全部存在）。它以磁盘文件为准而不信接口返回值，因为发布响应可能被服务端超时掐断而写盘仍在继续。

## 章节增补（一次加多章 / 补大纲）

1. 加章只走一个入口：管理页「②b 加章 / 补大纲」（或「菜单 + AI」页 → 大纲），选末尾追加或插到第 N 章之后。单事务入库，**绝不动已有章节正文**；任一项不合法（超 50 章、锚点章号不存在）则整批回滚，不留半插状态。三种方式：
   - **手写每章大纲**（📚 批量加章）：填「标题 + 大纲」若干行，大纲必填（无大纲的章不会被生成正文）。
   - **只填章数 + 素材**（🧩 区间补大纲·自动）：先按位置插占位章，再逐章把大纲写进去。手里只有素材、还没想好每章写什么时用这条。
   - **不新增章，只回填**（🧩 区间补大纲·回填）：只处理区间内大纲为空的章（包含模型兜底写下的「（无大纲内容）」），已有大纲一律跳过。
2. “自动 / 回填”两种模式都是一章一次模型调用：逐章串行（后一章能看到刚写好的前一章大纲，衔接才成立），所以章数越多越慢；单次上限 50 章，超出部分会告知“还剩几章”，重跑同一区间即可接着补。
3. 新章只有大纲、正文为空，此时发布不会产出这页（发布只渲染有正文的章）。补正文用「③ 区间生成正文」或「✍️ 生成正文」（chapter=0 / 不带 force），它们跳过已有正文、只补缺失章。
4. 「🧭 生成 / 重建全部大纲」是**整本重建**：会把命中章号的大纲/标题重写、正文清空。已有正文的书不带 `force` 会被系统直接拦下（聊天会话会弹确认卡片）。确实要重建时，被覆盖的章节会先存一份旧稿快照（`chapter_revision`，source=outlineRebuild），可回滚。
5. 个别章改大纲用「✏️ 更新章节大纲」，只改已有正文用「✏️ 修改章节」；二者都不触发上述关卡。
6. 章号不连续（历史手工删章导致跳号）时，批量加章仍会成功但会附提示，建议跑一次「🔢 重排编号」收敛。

## VIP 读者授权

1. 超管在小说管理页① 下方勾选「本书为 VIP 专属」并保存（只是给书打标）。
2. 再到控制台「💎 VIP 读者授权」选读者账号 + 范围（本书或全站 VIP）+ 有效天数，点「授予 / 续期」。
3. 无授权读者在站点首页看不到 VIP 书，直连书页会拿到无权页；撤销与到期每次请求实时生效。
4. 旧的「VIP 密码解锁」已整体停用（历史书页上的解锁按钮会收到 410 提示），请改用账号授权。


## 长任务反馈与推理链路预检

1. 管理页书名行右侧的 **🟢/🔴 灯** 是推理链路状态（点一下重探）。它只探桥接服务可达性与密钥是否已配（`/api/health`），**不计费**；绿灯也不保证上游模型一定可用，模型故障仍会报错。
2. 需要调模型的动作（生成/改写正文、全书大纲、区间补大纲、各部导言、设定说明）在**改任何数据之前**先过一次预检：不通就直接返回“本次未改动任何数据”并附上启动方式，不会先把章节插进目录再失败。预检通过的结果缓存 60 秒，失败不缓存（服务修好后下一次点击立即重试）。
3. 「🧩 区间补大纲」连续 3 章失败会自动停下，不再把剩下的章继续撞一遍（已经补成的章会重置计数）；失败报告只说实话：已插入多少个空位、原后续章顺延了多少章、还剩几章**未尝试**（未尝试不等于失败）。补完空位用「②b 回填」，不想要那些空位用「🗑 区间删除章节」。
4. 提交长任务后界面出现遮罩：转圈、已用秒数、以及服务端推进来的逐章日志。**600 毫秒内完成的任务不会闪出遮罩**；界面锁住到任务结束（含逐章循环的“③ 区间生成正文”，整轮期间遮罩不闪关）。前端不加超时兜底，以服务端 600 秒超时为准。
5. 生成类任务**按书互斥**（服务端锁，不只靠遮罩）：同一本书已有生成任务在跑时，第 2 次提交直接返回 409 并告知已跑多少秒。所以第 2 个标签页、另一台机器上的重复提交同样拦得住。发布/预览/体检只有遮罩与计时（服务端未埋逐章进度点）。

## 推理服务连接（aibridge API Key 切换）

1. 控制台「🔌 推理服务连接」（仅超管）：可以登记多条 aibridge API Key，点「启用」就换掉**后续所有生成走的那条**，**运行时生效、不用重启**（文生图代理也跟着走同一份配置）。只管“用哪条 Key / 哪个地址”，模型名、温度这些仍在桥接服务的 Key 上配。
2. 每条 Key 保存时会自动向桥接服务探一次身份（新增的 `GET /api/bridge/whoami`，**用 Key 自身鉴权**，不需要把桥接的管理口令搬进本工程），于是界面上能直接看到“这条连到 `Local` / `Qwen3.8-27B-…`”还是“`Ollama (远程)` / `gemma4:31b`”。旧版桥接没有这个端点时探测会报“桥接版本过旧”，但不影响存 Key 与切换本身。
3. **“连到哪个模型”就是这一节存在的原因**：实测同样一章正文，本地 `Qwen3.8-27B-ROCmFP4-FAST` 约 15 tok/s（单章中位 79 秒），`gemma4:31b` 约 217 tok/s（同类 4 秒），差一个量级。“生成很慢”先看这里的吞吐，而不是先改代码。
4. ⚠️ 探测结果里 `providerType` 为 `ollama_remote` 等公网服务时，界面会额外标「⚠ 公网」—— 选中它意味着**稿子要出公网**，与自建服务不是一个风险级别。
5. 明文密钥只存 `data/system/bridge.json`（写入即 `0600`，`/data/system/` 已在 `.gitignore`）；接口一律只回前缀（如 `abk_c826f132b…`），不回显明文。注意 `/api/admin/` 前缀的响应按设计不过净化（要回显地址），所以“不把明文放进返回值”是这边唯一的防线，改动该目录接口时务必守住。
6. 生效优先级：**控制台启用项 > `process.env` > `.env`**。把启用项停用、或删掉正在生效的那条，会自动回落 `.env`（界面上“来源”会从 `console` 变回 `.env`），不会出现“切没了就没密钥”的状态。
7. **重启后仍按控制台启用项走，而且启动日志会把链路打出来**：`bridge.json` 是惰性加载的，所以 `server.js` 在对外提供任何服务前显式调一次 `initBridge()`。原先启动路径上没人调它，“控制台切换”在重启后实际是哑的 —— 必须有人打开一次设置页才生效，中间所有生成静默用着 `.env` 那条 Key（实测踩过：控制台选了 Ollama 远程、正文却一直在跑本地 Qwen3.8，因为看不到链路归属，排查绕了很大一圈）。启动会打三行：`[bridge] 正文生成链路 …`（用的是控制台还是 `.env`）、`[bridge] 上游模型 …`（存过的探测结果）、`[bridge] 桥接侧确认 …`（真去问一次 whoami，只读不计费）。**怀疑“生成太慢 / 答非所问”时先看这三行**，不要从日志里的模型名去猜。
8. 地址覆盖只改 URL、不动 Key；只接受 `http/https` 完整端点，其余拒绝。切换后建议点一次「测活」确认桥接服务可达（这不计费、不计入模型吐量）。

## 章节字数

1. 三处可见：目录每章行右侧（蓝色）、分页条上的全书合计（“共 N 章 · 正文 X 字”）、以及看正文的弹层顶部（“正文 X 字 · 大纲 Y 字”）。设定页同样返 `totalWords`。一万字以上简写为“1.3万字”，无正文显示“—”。其中**大纲字数跟着输入框实时变**（正在改的时候报库里那份没有意义），正文字数仍是库里的值。
2. 章节弹层的“正文（只读预览）”**打开即自动加载该章正文**（以前要手动点“查看正文”，空框加占位语“尚未生成正文”会被误读成“这章还没写”）。拉的是单章接口，不是整本；真没正文时显示“（该章暂无正文）”。
3. **口径是存储字符数**（SQL `LENGTH(content)`，中文 1 字计 1），与既有 `wordCount: content.length` 同源，不另算一套；**不 trim**，所以换行与空行也计入。这不是 WPS/Word 的“字数统计”，两者对中英混排、标点的规则不同，对不上时以这个口径为准。
4. 顺带修掉一个真缺陷：`getAllChapters` 的 `includeContent` 参数**以前被完全忽略**，列目录会把整本书正文读进内存。现在不返正文、只返 `contentLength`。两处“重建大纲会清正文”的确认关卡原先就靠这个缺陷撑着，已同步改为看 `contentLength > 0`，否则判重会静默变成“全书无正文”、关卡失效且不问就清稿。

## 每章字数设定与字数治理

1. **每部小说一份共同设定，存在 `content` 表 no=0 行的 `gen_cfg` 列**（JSON：`{ targetWords, tolerancePct, splitPct }`）。生成正文与生成大纲都读它，而且提示词里写的是换算后的**区间**、不是“目标 N 字”一个数（实测同书里大纲 ~380 字的章正文飘到 2749–5608，而大纲 ~2000 字的章只飘 946——篇幅实际由大纲详略决定，只在正文提示词加一句管不住）。
2. 三个字段与边界：`targetWords` 300–20000（**0 = 不限**，默认 0）、`tolerancePct` 5–50（默认 20）、`splitPct` 20–300（默认 60）。**越界一律报错、不静默纠正**（填了 999999 却静默存成 20000，人不会知道）。换算：合格带 = 目标 ×(1±tolerance%)，拆章线 = max(合格上限, 目标 ×(1+splitPct/100))；3000/20/60 → **合格 2400–3600、超 4800 建议拆章**。
3. **口径只有一个来源 `src/utils/wordTarget.js`**：正文提示词、大纲提示词、生成后的长度判定、管理页显示的区间，四处共用 `effectiveBand`/`wordBand`/`bandText`。部名的中文数字就是这么分叉过一次的，不希望在这里重演——尤其不希望出现“页面说没设限、生成时却按某个数字要字”这种最难查的不一致。
4. 旧的 `【每章目标字数：N】` 文字标记（写在“角色/世界观设定”正文里）**只作回落**：一旦存过 `gen_cfg` 就不再读它，包括 `targetWords:0` 这种“显式取消限制”。原先 `if (cfg.targetWords)` 把 0 当未设、而且 0 时干脆不存这一行，结果是“取消限制”被设定正文里那句旧标记顶回去、成了无效操作；现在“存过”与“从未存过”在库里可区分。`saveNovelPlan` 的 `targetWordCount` 参数已改为直接写 `gen_cfg`，不再往给人读的设定文字里塞方括号（存量库里已有的标记不要求人手擦除）。
5. **四个入口、同一落库函数**（`db.saveGenConfig` 是唯一校验点）：① 管理页「小说设定」的三个输入框；菜单「🎯 每章字数设定」；AI 工具 `setGenConfig`；`PUT /api/novels/:id/settings` 带 `genCfg`。都是**未传即不改**的局部补丁语义（只改浮动比例不会把目标字数清零），显式 `null` 才是清除。`setGenConfig` **不传 `genCfg` 就是只读**，同时回“存了什么”与“实际按什么判定”两份，两者不一致就说明还在吃旧标记。
6. 「① 小说设定」保存只在**字段真的动过**时才携带 `genCfg`（进页面时留了一份快照做 dirty 比较）：否则用户只改个书名，就会顺手把字数设定按表单默认值重写一遍。
7. **设定只管之后的生成，存量章节要另外跑「📏 字数治理」**（`tuneWordCount`，同样三个入口）。按目标逐章定性五态并分流：`short` → 全文扩写（硬约束“只加不改”，扩完不比原文长就保留原稿）；`long` → 压缩（压过头掉到下限以下同样保留原稿）；`split` → **智能拆成两章**；`ok` 不动，正文 ≤50 字记 `no_body` 跳过。
8. 拆章为什么可信：**切点是纯算法选的**（按空行分段、逐段累加，落在不切断句子的边界），模型只负责给两半拟标题、写大纲——**两半拼回去就是原文**，不需要模型重抄上千字（让模型重抄，丢情节就是这么发生的）。上下两半的目标按实际长度比例分（`splitTargets`）而不是机械对半：4900 字对半是 2450、贴着下限，所以带“不低于 min”的兜底。**但兜的是目标值，不是实际切点**：段落是粗粒度边界，实测把 4958 字切成 2644+2327——上半偏到了 2631，下半就漏到下限以下了。所以现在候选切点先按“两半是否都在带内”过滤（不可行的加一个远大于任何长度差的惩罚），全不可行时才退回离目标最近，并把偏短的那半写进报告的 `reason`，下一轮治理会自动把它扩回去。副本库实跑第 7 章 5608 字 → 2953 + 2668，一次模型调用、约 20 秒，断言覆盖“逐字守恒 / 后续章号顺延 / 其余章一字未改 / 新章自动归进原章所属的部”。
9. **默认 dry-run 且开关只认真值**：`dryRun` 省略或认不准（例如手抖写成 `"yes"`）**一律停在预览**，绝不“解析失败就当 false”去开写正文；界面上的执行方式是个下拉、默认第一项就是“只看清单”，选“实际执行”要多输一次 `OK`。执行时按**章号降序**处理（拆章会把后面章号整体 +1，升序会拿着旧章号读到偏移后的章），单章失败只记进 `errors` 不中断整批。
10. 两处代价要知道：① **改的是正文与书结构**，需重新发布才会反映到读者站；② 拆章后旧章正文里的“第X章”字样会与新章号不一致——**页面标题看不到（发布端 `stripLeadingHeading` 会剥掉正文首行、按位置重建），但朗读、出题、选生词吃的是原始正文**，不修就会念出“第3章”而页面写着“第4章”。所以 `tuneWordCount` 拆完会连带校正偏移章里的「第X章」字样，而整个动作被拆成**固定顺序的三个阶段**：① 只执行拆章（拆完才有新编号）→ ② 编号定稿后统一校正**首行章号与正文/大纲里的互相引用**（报告里的 `headingFixed` 与 `xrefFixed`）→ ③ 才做扩写与压缩。②排在③之前是正确性要求而不是洁癖：扩写/压缩会让模型在**新**编号下写正文，之后再统一平移一次就把那些新写的引用移了**两**次，比完全不修更难查。③的范围包含拆出来的下半，偏短就同一轮自动补写，不再要求“再跑一次”。大纲尤其要改：下一次生成是照着大纲里的引用写的，留个旧号就等于把错误传下去。识别引用不另起口径，复用 `findChapterRefs`（已排除标题行，阿拉伯数字与中文数字两种写法都认）与 `toChinese`（还原写法：第五章→第七章，不是第7章）；旧号大于拆章前最大章号时原样不动并记进 `xrefUnresolved`，因为那不会是平移的结果。改动前都会先存 `chapter_revision` 快照，但**别把它当后悔药**：快照按章号回滚，拆过章之后章号已错位，回滚会砸到别的章上——真正的安全边界是“内容守恒 + 执行前那一次确认”。
11. 一次真实生成的实测（本地 Qwen3.8，目标 3000 字）：**169 秒、3684 字**，超上限 84 字，结果里会明写“超出合格上限，可用字数治理压缩”而不是静默偏离。这个耗时也说明为什么必须调超时，见下一条。
12. **跨服务超时是这道设定的真实约束**：aibridge 对上游原本硬编码 120s，而本地模型约 12–25 字/秒，3000 字的整章生成实测就在 120s 被切（表现为 502，看着像“设了字数就写不出来”）。现在 `POST /api/bridge/chat` 接受调用方传的 `timeout`（钳在 10s–280s；280 是因为 Node `server.requestTimeout` 默认 300s，再高只会变成 `socket hang up`），ainovel 侧按产出量给预算：`_chapterCallMs = min(280s, max(120s, 60s + 100ms × 目标字数))`，正文生成、续写、扩写、压缩四条长产出路径共用。
13. 自检：`node tmp/word-check.mjs`（49 项，纯本地不碰网络，覆盖区间边界、越界拒绝、旧标记回落、显式 0、dry-run 前后库摘要一致）、`node tmp/word-split-check.mjs`（15 项，**只在 `tmp/` 副本库上真调模型拆章**）、`node tmp/word-gen-check.mjs`（一次真实整章生成，副本库、全程只读）、`node tmp/cp-selftest.mjs`（内容级闸门自检：10 项构造样本 + 全库拆章无损核，只读线上库、不调模型）。
14. **扩写必须过内容级闸门，而且判据顺序不能反**。`_expandChapterToTarget` 拿到结果先算“原稿是否一字未动”（`_contentPreservation`），两条互补判据：① 剔除标点/空白/Markdown 记号后求**字符保序最长公共子序列**（删句、换词、调序会立刻掉下来，纯插入必然等于原稿长度）；② 原稿按标点切成的**片段必须连续命中**（补住①的盲区：“他推开门”→“他缓缓推开了那扇沉重的木门”在字符粒度上就是纯插入，只能靠片段连续性拦）。不成立就**整章放弃、保留原稿**——字数不达标只是这一章还短，原稿被覆盖是不可逆的内容损失。两条都成立之后才看“新插段承载率”与“台词承载率”判灌水（先测增量不测子集关系，会把改写原稿的稿判成 100% 合格——第一版就是这么反向的）。
    **首行标题不参与核对**：它由 `normalizeChapterHeading` 按当前章号重写，不是模型保真度的对象。漏了这一条会构成一个隐蔽的死锁：拆章把下游章号整体后移，但那些章正文里的旧章号没人负责改，于是原稿片段“第10章”必然在新稿里消失（已被修正为第14章）——实测就是第 14 章内容保留 99.95% 仍被拦，丢的那 1 个字就是标题里的旧章号。豁免仅限首行：`cp-selftest` 里专门有一正一反两条（标题修正→放行，标题修正但正文丢一段→仍拦下）。它的另一段断言是“拆章无损核”——把执行前快照（`tmp/backup-before-tune/`）里每个备份章的长段落归位到现稿章，再用生产同一判据核它是否一字未动；比对前先涂掉「第X章」里的**编号**（留“第…章”外壳，涂成“第零章”）：编号修正后正文不再与快照逐字相同，而整串涂成一个记号会让 `_contentPreservation` 的 `unh1` 认不出标题行、把拆章时改掉的老章名当成丢失片段报出来（实测因此误报 3 章）；拆出的 5 章映射为 2→2+3、3→4+5、7→9+10、8→11+12、9→13+14，全部无损，被压缩的章从 `chapter_revision` 的「压缩前」记录推得、不参与无损判定。
15. **压缩允许重试一次，且回喂必须在硬守卫之前**。只不低于下限就算成功的话，“压到 2400 附近”会被当成合格交付：实测一章 3732→2402，目标 3000 只需砍 20%，它砍了 36%，多丢的那一大截没人授权过。所以现在结果低于 `目标×0.85` 就追加一条“不得少于 N 字、把被整段删掉的场景补回来”再要一次，两次都偏短就用更接近目标（也就是丢得更少）的那次。顺序重要：3775 字那章第一次只回 2252 字（已跌穿下限），若先在硬守卫处 `return` 就永远不会重试——实测重试后落在 3162，接近目标。
16. **拆过章之后要跑一致性体检**：`checkChapters`（`scope:"all"`）里的确定性检查就是为这类结构变更准备的，`heading-number` 一项能拦住刚才那个旧章号问题。它不在 `/api/run` 的 action 白名单里（那是安全相关的清单），本地可用 `node tmp/run-check.mjs` 直接调同一个函数（零模型调用）。配套工具：`tmp/tune-structure.mjs`（整本 dry-run / 降序逐章执行，两路互证判定）、`tmp/verify-split.mjs`（内容守恒 + 章号连续 + 字数进带；段落是整段逐字命中，所以「第X章」的编号修正要涂掉再比，理由同上一条）、`tmp/fix-heading-shift.mjs`（补修存量旧章号，默认 dry-run）、`tmp/fix-xref.mjs`（补修存量正文/大纲的互相引用，默认 dry-run）。后者留了三道只有存量修复才需要的关卡：拆章点从 `chapter_revision` 取而不写死；公式映射与“按内容归位反推”两路互证，不一致就停机；每处改动必须能在执行前快照里逐字回指到上下文（回指不到 = 拆章之后新写的，本来就是新号，改了反而制造错误），写盘前再把编号遮成同一个记号硬比一次，两边逐字相同才写。本轮跑下来改的是 10 章 80 处。

## 章节编辑弹层（在③ 里点某章进来的这一层）

1. **可就地翻章**：顶部有「‹ 上一章 / 下一章 ›」，按钮上带邻居章的标题（只写“下一章”三个字看不出要不去），没有邻居时置灰。切换是原地重绘 + 0.22s 的**方向性入场动画**（下一章从右进、上一章从左进），标题/大纲/正文/字数都跟着换。`←` / `→` 是同一个动作，但只在弹层开着、焦点不在输入框、且没有更上层的 OK 确认时生效。背后的章节列表会同步翻到本章所在页，关掉弹层不会跳回第 1 页。
2. **翻章会拦未保存的改动**：弹层是原地重绘的，手打的字一丢没有第二次机会，所以标题/大纲与库里那份不一致时先问一句。判据是**按值比较**而不是“有没有敲过”——改回原样照样放行，内容一致时压根不打扰。
3. **「本章构思」输入框 + 「🧭 生成大纲」**：填一句这章要写什么（留空则只按故事概要与前后章衔接构思），点生成 → 结果**填进「章节大纲」框**，可以直接改，改完点「保存大纲」才落库。接口 `POST /api/novels/:id/chapter/:no/outline-draft`，**全程只读**：实测调用前后整本 `.db` 文件 md5 一字未变、各表行数一致、本章标题/大纲/正文原样，所以“不满意就直接关掉弹层”是安全的。它带小说概要与紧邻两章的大纲当上下文，与「②b 区间补大纲」用的是同一个生成函数（区别就在那条会直接落库、且跳过已有大纲的章）。
4. **生成的是草稿，所以不设“确定覆盖吗”**：填进输入框前那份留在内存里，状态行给一个「↩ 换回生成前那版」。模型另给了标题时**不覆盖你手打的标题**，只在状态行写「模型建议标题「X」　采用」。解析失败时模型会把标题兜成“第N章”，那不算建议，接口不返。
5. **这是一次完整的模型调用，实测 57 秒**（本地 27B，产出 1012 字大纲，单样本）。遮罩会写明「🧭 生成本章大纲（一次模型调用，可能要一分多钟）」；失败（典型是 aibridge 没启动）把原因**写在弹层里那一行**，而不是写背后被盖住的结果区——否则就是“等了一分钟输入框纹丝不动”。
6. **「保存大纲」成功后不再自动关弹层**：有了翻章，“改一章→翻下一章”是连续动作，每次重开太碎。反馈改成弹层内联的「✓ hh:mm:ss 已保存」，保存后又动了笔这句话会自动消失。
7. **「生成正文」用的是库里那份大纲**，不是输入框里这份：有未保存改动时先问一句并默认“保存完接着生成”（原先不问就开跑，等于拿旧大纲生成、还顺手丢掉刚打的字）。
8. 守卫都在调模型**之前**：没故事概要 → 400（不调模型）、章号非法 → 400、章不存在 → 404、链路不通 → 502、模型没给可用大纲 → 502（不把“（无大纲内容）”当草稿交付）。这些路径全部在调模型前后就返回，**不写库、也不参与按书加锁的生成任务队列**（它只读）。

## 分部划分（把若干章归为一个“部”）

1. 入口：管理页顶部「菜单 + AI」标签 → 「设定/分部」组 → 「📚 划分部」。同组还有「👀 查看部结构」（看现状：各部起止章、有没有导言）和「🧭 生成部导言」（留空部序号 = 全部）。
2. **输入方式是行输入框，不再手写 JSON**。每部一行，只填两件事：部名、**到第几章**。起始章自动接上一部的末尾——因为服务端要求各部从第 1 章起**连续覆盖到全书末章**、不得重叠（有缺口/重叠会报错并列出缺哪些章），所以起始章本来就没有自由度，让人填只会制造错误。
3. 最后一部的结束章**可以留空**（= 全书最后一章）；若填了一个小于末章的数，会**自动把最后一部收到末章**，弹窗里的预览行会当场写明（形如“第一部 1–5（5章）　第二部 6–10（5章）　末部已收到第 10 章”）。预览与提交用的是同一份推导算法，所以所见即所得；填错（结束章倒退、非整数、越界、中间部留空）当场显红色 ⚠，不发给服务端。
4. 部名可留空，留空时由系统按序号命名（`saveParts` 存空字串，显示层再补：读者站与返回文本里是“第一部”“第十一部”这类中文序数，而 `_buildOutlineContext` 等提示词里空名会写成《未命名》）。想撤掉划分用弹窗里的「🗑 清除全部分部」，它只解除归属，**不删任何正文**，之后可重新划分。
5. 两个代价要知道：① 改区间等于换了一部（导言按“起–止”复用），**原部导言会丢**且导言页文件名会变，改完需重新生成导言；只改部名不丢。② 部结构只在**发布后**才看得到（读者站按部成组、章节页顶部显示部名），管理页的章节列表不显示部归属。

## 改名（章节标题 / 部名）

1. **章名**：「流程管理」→ ③ 章节列表→点某章→弹层顶部「章节标题」框改了再点**「保存大纲」**（这个按钮同时保存标题与大纲，名字取自接口名；保存后弹层不关，见「章节编辑弹层」第 6 条）。另一个入口是菜单「✏️ 更新章节大纲」。**URL 不变**：章节页文件名是 `chapter_<稳定章节id>.html`，不吃标题，所以改名不会让已分享出去的链接失效。
2. **标题不能改空**：服务端判的是 `if (name)`，空字串会被当作“没传”而**忽略**（好处：不会误清空标题；代价：想把标题改成空做不到）。“保存大纲”只改标题时也会回“已保存”，以列表里的实际文字为准。
3. **部名**：没有单独的改名入口，就是在「📚 划分部」里**只改部名、保持每部的结束章与原状一致**。区间一致则复用同一个部 id（`saveParts` 的幂等键是 `起|止`，不含部名），所以**部导言不丢、导言页 `page_<id>.html` 文件名也不变**；区间一改就等于换了一部，原导言会丢。
4. **弹窗会自动预填现有分部**（新接口 `GET /api/novels/:id/parts`，只读，返 `no/name/startNo/endNo/chapters/hasIntro`，**不返导言正文**），所以改名就是把部名那一栏改掉再执行，不必先抄区间。预填只在结构能忠实表达时进行，否则会在弹窗里写清楚：有缺口时提示“第 X、Y 章现在不属于任何部，执行后会被并入后面的部”，有空部时提示“另有 N 个空部将被移除（含其导言）”；接口读不到则回落默认两段并说明。
5. 两者改完都只存在库里，**读者站要重新发布才更新**（想先看不影响线上可用「👁 预览」）；管理页里章节列表会立刻刷新，部名则只能靠「👀 查看部结构」确认。
6. 已修一个静默丢数据的缺陷：菜单/AI 那两路只改标题而不带 `outline` 时，`undefined` 会被 better-sqlite3 **绑成 NULL 且不报错**，等于把那章大纲清空并回 `success:true`。现在 `updateChapterOutline` 把 `undefined/null` 视为“不改大纲”而沿用原值，显式传 `''` 仍是清空（REST 接口原本就有这层兜底，现在改由落库口统一保证）。

## 阅读模式（学习模式）

1. **入口全在读者页工具栏**，不在管理页：学习模式开关、「📝 测试」（本章小测试）、「词汇讲解」面板、设置里的「学习语言」（英语/日语/韩语/中文）与年龄档。服务端是 `/api/reader/` 下的 `quiz`/`explain`/`vocab`/`explain-word`/`word-status` 五个端点，**注册在 `requireAuth` 之前**（未登录读者也能用，故另有 `readerRateLimit` 限流）。
2. **默认讲解语言 = 中文**（`reader.core.js` 的 `learnLang()` 兜底与下拉 `selected` 一致），理由是它要匹配已预热的中文词表：没动过设置的人一开页讲解就是黑体、秒显。选其他语种时自动生成长得像“每次从零开始”（英文当时只有 45/183 个词有缓存）。该兜底**只对从未存过这个设置的人生效**——localStorage 里有值时以它为准，所以自己的浏览器看到旧语言是预期的，选一次即覆盖。
3. **缓存键的口径是这套设计里唯一不能错的点**：生词表与测试题都用 `sha1('vocab|quiz' + 年龄 + 正文)`，正文一改写键立刻变，不可能拿到过期结果（绝不能图省事改用章节号或文件名做键）；讲解文本另建一键，含 `词 + 年龄 + 语言`。三类数据与 TTS 音频都落在 `global.db` 的单表 `reader_vocab` / `reader_word_explain` / `reader_quiz` / `reader_tts_audio`，并做**有界淘汰**（匿名接口可被任何人刷，无上限等于无界增长的库）。
4. **发布时预生成**拼音、章节测试、生词表并内嵌进书页（读者打开零 LLM、即时呈现）；占位章不参与，避免白跑推理。点词讲解则是按需生成 + 持久缓存，一次生成全站复用。测试面板里的「换一组新题」是唯一会带 `force` 的路径，它先作废旧缓存行再重跑，以免新跑失败后留下新旧混用的结果。
5. 改 `reader.core.js` **既不用重启服务也不用重新发布**：`reader.js` 以 `?v=Date.now()` 带时间戳加载 core，永不命中浏览器缓存；静态资源本身也只是 `max-age=0` + ETag，文件一变 ETag 就变（已实测）。

## 删除操作的二次确认

1. 删除类操作都要在弹层里**手输 `OK`**（仅“去空白后等于大写 OK”才放行，输入框没填对时确认按钮是灰的）：删整本小说、删单章（会告诉你删的是哪一章、标题是什么）、区间删除。
2. 区间删除**整批只确认一次**（弹层里写明“第 X–Y 章、共 N 章”）：逐章都弹的话删 20 章就要输 20 遍，等于不可用。但服务端校验不打折，循环里每一章的请求仍各自带着 `confirm:"OK"`。
3. 确认不只做在界面上，**三个入口服务端都拦**：管理页的 REST 接口、命令行/直连的 `/api/run`（`action` 为 `delete`/`del`/`d` 时需带 `confirm:"OK"`）、AI 对话的 `/api/ai/execute`（工具为 `deleteChapter` 时）。AI 那一路由「确认执行」卡片随请求带上 `confirm`，那一次人工点击就是确认；绕过界面直打该端点会被 400 拒。
4. 不要求确认的：“保存章节标题/大纲”（每章编辑都要点，加确认会把日常操作堵死）、以及“生成正文”（它不删数据；整本重建大纲另有 `force` 关卡）。其余非删除类操作仍是普通确认框。
5. **发布**只确认**一次**（点一下即可，不要求输 OK）：弹层把“读者将看到什么”摊开——线上是否已有本书（有则直接覆盖读者正在看的页面，且**本次不再产出的旧章节页会被删掉**）、共几章 / 几章还没正文（那些会被发成「本章尚未完成」的占位页，判据与 `publish.js` 的 `isPlaceholder` 一致）、以及可能要几十秒。两个信息源（`/share`、章节列表）任一探测失败都只是**少说一行**，不编数据也不拦发布。
6. 发布这道确认**只做在界面上**：`POST /api/novels/:id/publish` 服务端不拦（与上面「不强制未预览不能发布」的既有决策一致），AI 工具 `publishNovel` 也未加闸门；逐章自动发布走 `_autoPublishIfNeeded` 的进程内调用，本来就不经过这个端点。预览页「✅ 确认发布」已有一道 `confirm`，且修改报告里本就写着「待下线（发布时删除）」的页数，不再叠加。
7. 静态文件改了**不需要硬刷**：服务发的是 `max-age=0` + ETag（`size-mtime`，**size 那一位是十六进制**，别拿十进制去对），文件一变 ETag 就变（已用 `touch` 实测）。阅读器那边更宽松：`reader.js` 以 `?v=Date.now()` 带时间戳加载 `reader.core.js`，永不命中缓存。
