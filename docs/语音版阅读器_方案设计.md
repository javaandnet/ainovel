# 语音版阅读器 方案设计（服务端 TTS 音频）

> 状态：**待实装**。前提结论已全部实测，不含推测。
> 目标：解决浏览器 `speechSynthesis` 在**息屏/锁屏后被系统挂起**的问题，让"只听声音"在 iOS 与国产浏览器上也有保证；
> 同时保留现有网页版（浏览器合成），两种形态并存可比较。

## 1. 一句话结论

**在服务器上调用 edge-tts 可行**，但不要用 Python 版 —— 线上只有 Python 3.6.8（`edge-tts` 要求 ≥3.8），
改用 Node 端口 [`msedge-tts@2.0.7`](https://www.npmjs.com/package/msedge-tts)（纯 JS、无原生编译、2026-07 仍在维护），
直接跑在服务器已有的 node v22.23.2 上。已在线上实测出声成功。

## 2. 实测事实（本方案的依据）

| 项 | 实测结果 | 含义 |
|---|---|---|
| 线上 Python | 仅 `/usr/bin/python3` = **3.6.8**，无 conda | 装 Python 版 edge-tts 需额外塞独立解释器 → 放弃 |
| 线上 Node | v22.23.2 / npm 10.9.8（nvm 路径） | 与 `ainovel` 同运行时，零新增依赖面 |
| 线上出网 → 微软语音端点 | `speech.platform.bing.com` TLS 通，404 / 0.19s（路由可达） | 无防火墙障碍 |
| **线上合成实测** | `SERVER_SYNTH_OK 耗时ms=379 字节=47520`（18 字 → 7.9s 音频） | **服务端按需合成成立**，未被限流/封 IP |
| 本机合成实测（Python 版） | 2.12s 首帧握手 / 48kbps mp3 + `.vtt` 句级时间戳 | 协议可用；Node 版同样给句级 offset |
| Node 版本地产物 | `audio.mp3` + `metadata.json`（`SentenceBoundary` 含 `offset`/`duration`/`text`） | 句级对齐数据齐备，高亮不必猜 |
| 服务器资源 | 3 vCPU / 2000MB（可用约 994MB）/ 磁盘 **22G 空闲** / glibc 2.17 | 合成进程瞬时约 60–80MB，可接受；不做常驻 |
| 内容体量 | 46 章有正文，**中位 1,484 字/章**，全库 86,015 字 ≈ 朗读 270 分钟 | 全库音频 **约 100–115 MB**（48kbps 单声道） |

> 合成成本：edge-tts 走微软公开边缘接口，**免 key、¥0**。正式云 API（Azure/阿里云神经音色）留作协议失效时的兜底，
> 全库一次性合成也只需十几到几十元量级（8.6 万字符）。

## 3. 架构

```
发布/首次朗读
   │  句子文本（沿用 reader.core.js 现有逐句切分结果，一字不差）
   ▼
POST /novel/api/tts/sentence   ←— 存在性校验：只接受确实出现在该章正文里的句子
   │
   ├─ 缓存命中 ──────────────► 200 + mp3（或 302 到静态路径）
   └─ 未命中 → 单飞队列（并发≤2）→ msedge-tts 合成 → 落盘 → 返回
   │
   ▼
data/tts/<hash[:2]>/<hash>.mp3        hash = sha1(句子文本 | voice | rate)
```

**音频路径由 DB 管理**（与 `reader_word_explain` / `reader_quiz` 同构）：

```sql
CREATE TABLE IF NOT EXISTS reader_tts_audio (
  hash TEXT PRIMARY KEY,           -- sha1(text|voice|rate)
  voice TEXT NOT NULL,
  rate TEXT NOT NULL,
  file_path TEXT NOT NULL,         -- 相对 data/tts/
  bytes INTEGER NOT NULL,
  created_at INTEGER NOT NULL,     -- epoch ms
  last_accessed INTEGER            -- LRU 清理用
);
```

好处：可查询库存（多少句有音频、占多少磁盘）、按 `last_accessed` 做 LRU 清理、hash 去重显式、后续加状态字段方便。

- **音频是句子粒度**，不是整章拼接。理由：现有全部交互（逐句高亮、进度条按句索引跳转、点句朗读、
  连读跳章、定时关闭）都建立在句子序列上，换成整章音频 + seek 要重写定位逻辑，收益仅是消除 100–200ms 句间间隙。
- 缓存键含 `voice|rate`，所以换音色/语速自动分键；**正文改一个字只有那一句重新合成**，其余继续命中。
  同一句在多章重复出现只合成一次。
- **合成不常驻**：只在未命中时拉起 `MsEdgeTTS` 实例，用完 `close()`。379ms/句，一章约 25 句 →
  首读一章最坏约 10 秒，且第一句 0.4 秒即可出声（前端边播边预取后面的句子，见 §5）。
- 静态化：音频落盘后由现有静态中间件直出，`hash` 文件名天然 immutable，不需要缓存失效策略。

### 3.1 防滥用（必须先设计，不能事后补）

一个"传文本、返回音频"的公开接口 = 免费 TTS 开放代理，会被刷。约束：

1. 请求必须带 `book` + `chapter` + 句子文本；服务端读取该章正文，**确认该句确实存在于正文中**才合成。
2. 单 IP 令牌桶限流 + 同章并发合并（同一句并发请求只合成一次，其余等待复用 —— 现有 `aiService.enqueue` 同构）。
3. 每日合成句数上限（超出只服务已缓存句），超限记日志不静默。
4. 音色白名单（只放开 `zh-CN-YunxiNeural` / `zh-CN-XiaoxiaoNeural` / `zh-Tw-YunHsiaoNeural`… 实际启用的几个），
   `rate` 只接受面板那三档 —— 否则键空间被任意参数打穿。

### 3.2 失败降级

合成失败（微软改协议 / 限流 / 超时）→ 接口回 `503 {fallback:"browser"}`，**前端自动切回 `speechSynthesis` 并提示一次**，
阅读不中断。也就是说音频引擎永远只是加速层，不是单点。

## 4. 两种网页如何并存

书页是发布时烧死 HTML 的构建产物（52 页），**不为比较而发布第二套页面** —— 那会要求全站重发，且此后每个功能都要维护两份。
改为同一页面两种引擎，两条入口都可用、可直链分享：

| 形态 | 进入方式 | 朗读宿主 | 特性 |
|---|---|---|---|
| 网页版（现状，默认） | 直接打开书页 | `speechSynthesis` | 零服务器负担；息屏后是否出声看设备脸色 |
| 语音版 | 面板「引擎」切到 `🔊 音频`，或链接带 **`?engine=audio`** | `<audio>` + 服务端 mp3 | 锁屏/后台/蓝牙耳机可控，息屏必定出声 |

- 选择后写 `localStorage.ttsEngine`，跨章连读保持（与 `ttsRate`/`ttsKeepScreenOn` 同一套偏好机制）。
- 顶部目录/分享面板各加一个「语音版」直链（`?engine=audio`），便于两台手机横向比较。
- **默认仍是网页版**，观察一段时间音频版稳定性后再议是否翻转默认（与上次常亮默认值翻转同类决策，不顺手夹带）。

## 5. 交互在音频引擎下的等价实现

| 现有能力 | 音频引擎实现 |
|---|---|
| 逐句高亮 + 自动滚动 | `audio.onended` → 下一句；句内进度用 `metadata.json` 的 `offset/duration` 可选细化 |
| 进度条拖动跳句 | 不变（仍是句子索引定位），只是换宿主 |
| 点句/双击朗读 | 不变 |
| 连读跳章 | 不变；跨页时音频引擎在下一章重新接管 |
| 定时关闭（分钟档 / 本章结束） | 不变，逻辑与宿主无关 |
| 生词加粗、点词查询、AI 问答、测试 | 不受影响 |
| 语速 | `rate` 进合成参数与缓存键（0.7/1.0/1.5 → `-30%/+0%/+50%`），**注意音频语速改变会重合成** |
| 音色 | 面板音色需映射到 Edge 音色名；不在映射表内的音色自动落回网页版引擎并提示 |

### 5.1 已知的浏览器策略差异

`<audio>.play()` 在非用户手势下会被拦（iOS Safari / Chrome autoplay policy）。
**跨章 `?autoplay=1` 正是这种场景** —— 现有代码已为此准备了 `spokenOnce` 检测与"请点击 ▶ 播放"降级提示，
音频引擎沿用同一套判定（`play()` 的 Promise rejection 即视为被拦，落回提示），不需要新机制。
同页内逐句连续播放不受影响（手势链已建立）。

### 5.2 Media Session（两种引擎都受益）

`<audio>` 宿主天然可挂 Media Session：书名/章名/第几句 + `play/pause/prev/next/seekto` 路由 → 锁屏与耳机出现控件。
网页版则把控件挂到现有的静音保活 `<audio>`（它已经在占音频会话）上，动作转成对 `speechSynthesis` 的 resume/cancel。
这一项与引擎无关，可独立先上。

## 6. 实装拆解

| # | 改动 | 文件 | 量 |
|---|---|---|---|
| 1 | 引擎抽象 `speakSentence()` 二选一宿主（`speechSynthesis` / `<audio>`），保留全部现有分支 | `public/tts/reader.core.js` | 中 |

### 验收清单

- [ ] 线上 `POST /novel/api/tts/sentence` 首句 <1s 出声；二次命中 <50ms

## 7. 风险登记

| 风险 | 影响 | 对策 |
|---|---|---|
| edge-tts 是非官方接口，微软可变 | 新句无法合成 | 已设计为**加速层**：失败自动回落网页版；兜底可切 Azure key（改动仅在 `ttsStore`） |
| 服务器 IP 被限流 | 首读变慢/失败 | 并发≤2 + 退避重试 + 批量预生成把调用摊到低峰时段 |
| 正文重发导致句子变化 | 重新合成受影响句（不可避免） | 键即内容哈希，自动只补差异；旧文件按 mtime 周期清理 |
| 磁盘增长（后续章节变多） | 每 100 章约 +200MB | 当前 22G 空闲，阈值告警在 80% 时清最冷音频（可重合成，删了不心疼） |
| 音频与网页版行为不一致引入新 bug | 阅读体验回退 | 默认仍是网页版；语音版按链接隔离，可逐台设备灰度 |

## 8. 回滚

关掉即回到现状：`reader.core.js` 单文件回退（远端已有 `.bak.*` 存档），服务端路由与 `data/tts/` 留着无害、不阻塞任何功能。
